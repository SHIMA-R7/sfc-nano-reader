# 開発史

このダンパーが動くようになるまでの記録です。**うまくいったことより、間違えたことを重点的に**
書いています。同じ地雷を踏む人を減らすためと、「なぜこの設計なのか」を残すためです。

診断を誤った箇所には、何を根拠に誤り、何で気づいたかを明記しています。

---

## 第1章 構成を決める

出発点は「ESP32-S3の開発ボードとジャンクのスーパーファミコンがある。これだけで吸い出せないか」
でした。

SFCカートを読むには最低でも **アドレス24本 + データ8本 + 制御2本 ≒ 34本** のI/Oが要ります。
検討した候補:

| 案 | 却下/採用の理由 |
|---|---|
| ESP32-S3 単体 | **5Vトレラントではない。** カートの5V出力を直結すると壊れる。レベル変換ICが必須だが手持ちなし |
| Arduino Uno 単体 | 5Vネイティブで電圧問題なし。しかし使えるI/Oが18本しかなく、34本には遠く及ばない |
| Arduino Mega 2560 | I/O 54本で直結でき最も素直（Sanni's Cart Readerがこの構成）。**ただし買い足しが必要** |
| Raspberry Pi Zero 2 + Nano | 3.3V系のためデータバス8本＋ACKに分圧抵抗が18本ほど必要。「手持ちだけで完結」の利点が消える |
| **Nano × 3** | **採用。** 全ボードが5Vネイティブで電圧問題が原理的に発生しない。追加部品ゼロ |

制作者の縛りが「追加で一つもパーツを購入しない」だったため、最後の案に決まりました。

途中でESP32-S3を「バスに触らない受け皿（UART受信＋WiFi転送）」として使う案も検討しました。
バスマスタとして使うのが問題だったのであって、受信専任なら電圧問題は起きないという整理です。
結局はPC直結で足りたため採用しませんでした。

## 第2章 コネクタという物理的な壁

### 62ピンは表31＋裏31

「62ピン」を表裏で124本と誤解しがちですが、カードエッジは基板の両面に端子が並んでいて、
それをまとめて挟むタイプです。合計62本で正しい。

さらに、62本のうち相当数はGND/VCCの重複です。実際に配線が必要なユニーク信号は
アドレス24＋データ8＋制御2＋電源/GND数本で足ります。

### ピッチは2.54mmではなく2.50mm

制作者から「ユニバーサル基板に微妙に合わない」という報告があり、当初は
「2.0mmピッチだから31ピンで大きくずれる」と回答しました。**これは誤りでした。**
「それなら20ピンで1cmずれる、それでは刺さるはずがない」と指摘され、調べ直したところ:

- 実際のピッチは **2.50mm**（2.54mmとの差は0.04mm、31ピンでも累積1.2mm程度）
- **列間隔とキー溝の位置も非標準**

つまり主犯はピッチの累積誤差ではなく、列間隔とキー溝の変則さでした。
制作者はキー溝を超音波カッターで切断し、金属シールドで位置決めして押し込むという
力技で解決しています。

**教訓: 数字が合わないと言われたら、自分の記憶ではなく資料を当たる。**

## 第3章 最初の設計と、そこに埋めた欠陥

3台の役割分担:

| ボード | 役割 |
|---|---|
| Nano-1 | アドレス A0-A15。STROBEパルスで16bitカウンタを+1 |
| Nano-2 | `/RD`・`/ROMSEL`制御、D0-D7読み取り、USBでPCへ送信、OLED表示 |
| Nano-3 | アドレス A16-A23（バンク）。**Nano-2から DATA/CLK/LATCH の3線シリアルで受信** |

Nano-3だけ方式が違います。これが後で牙を剥きます。

## 第4章 動き出すまでに踏んだ地雷

### 全部 0x00 になる

原因は**カートが挿さっていなかった**。制作者の申告で判明。
以降、トラブルシューティングの筆頭に「まずカートが挿さっているか」を書いています。

### 同じ値が2回ずつ並ぶ

アドレス最下位ビットが効いていない典型的な症状に見えました。配線を疑いましたが導通は正常。
実際は**待ち時間不足**で、`/RD`アサート後の待ちを1µs→100µsにして解消。

### 32KB周期で内容が繰り返す

「A15の配線不良」と判断して制作者にハンダ付けをやり直してもらいましたが、**変化なし**。
これは故障ではなく、**LoROMではバンク内の上位/下位32KBが同じ内容にミラーされる**という
正常な電気的挙動でした。無駄な作業をさせてしまった箇所です。

### 実行のたびにデータ位置がずれる

Nano-1のアドレスカウンタが起動時に0から始まっていませんでした。
Nano-2 D10 → Nano-1 A5 に **ADDR_RESET線を1本追加**して解決。

### 1バイトずれる

ストローブを1回余計に打って補正しようとしたら**2バイトずれた**（対処が逆方向）。
本当の原因は**PC側スクリプトがシリアル受信バッファをクリアしていなかった**ことで、
前回セッションの残留バイトを読んでいました。`reset_input_buffer()` と
「要求サイズちょうどだけ読む」の2点で解決。

**教訓: ハードを疑う前に、自分のホスト側コードを疑う。**

## 第5章 最大の落とし穴 — ヘッダのチェックサムは何も保証しない

ぷよぷよの1MBダンプが取れ、内部ヘッダの検証も通ったので「成功」と報告しました。

**これは誤判定でした。**

SNESの内部ヘッダには「チェックサム」と「その補数」が入っており、
2つのXORが `0xFFFF` になるかを見るチェックがあります。しかしこれは
**ヘッダの4バイトが正しく読めたことしか保証しません**。ROM本体が壊れていても通ります。

発覚したのはエミュレータに読ませたときで、Snes9xコアが `Invalid Checksum` を出力しました。
正しい検証は **ROM全体のバイト総和** です。

```python
checksum = rom[off+30] | (rom[off+31] << 8)   # ヘッダが主張する値
computed = sum(rom) & 0xFFFF                  # 実際に計算した値
```

以降、この総和とNo-IntroのCRC32の両方で検証しています。

## 第6章 バンク転送の設計ミス

本体が壊れている原因を追うため、一晩かけて20回以上ダンプし、バイト単位の多数決で
マージしました。結果、**特定のバンクだけが毎回丸ごと化ける**ことが判明。

原因は Nano-2 ⇔ Nano-3 の3線シリアル転送でした。2台は**別々の水晶発振子で非同期に動く**ため、
クロック同期でビットを取りこぼします。パルス幅を5µs→300µsに広げても完全には安定しませんでした。

**解決: Nano-1と同じ「STROBEでカウントアップ」方式に統一。**
バンクは常に0から+1ずつ進むだけなので、シフトレジスタである必要がそもそもなかった。
クロック同期という概念自体が消え、原理的に安定します。

配線は変更不要でした。旧DATA線をRESET、旧CLK線をSTROBEとして読み替え、旧LATCH線は放置。
誤り率が数十万バイトから数千バイトへ、**約100分の1**に激減しました。

その後27サンプルの多数決マージでぷよぷよのチェックサムが一致し、**1本目が完成**しました。

## 第7章 スーパーマリオコレクション — 24回読んでも合わない

2本目で最も長く詰まりました。

### マッピングの誤判定

バンク0の前半32KBと後半32KBを比較し、「一致しない＝ミラーなし＝**HiROM**」と判定しました。

**これが誤りでした。** 前半は単に**全部0x00で死んでいた**だけで、それを「別内容」と読み違えていました。

さらに悪いことに、ヘッダの `map_mode` バイトは `0x20`（＝LoROM）と**最初から正しく読めていた**のに、
自分の推論を優先して「HiROMなのに0x20とは妙だ、ビット落ちか」と疑ってしまいました。

### この誤判定が引き起こしたこと

LoROMではROMは各バンクの `$8000-$FFFF` にしか現れません。したがって:

- 2MBのLoROMには**64バンク必要**（32KB×64）なのに、32バンクしか読んでいなかった
- しかも**データのない下位32KBの方を採用**していた

出来上がったのは「実データ1MB＋ゼロ1MB」。**24回ダンプしようが多数決を取ろうが、
合うわけがありませんでした。**

ぷよぷよは上下がミラーだったため下位半分でも正解になり、その成功体験に引きずられました。

### 途中で立てて否定された仮説

| 仮説 | 検証結果 |
|---|---|
| 誤りは「ビット落ち」の一方向のみ。だからORマージが正しい | **誤り。** 基準に多数決値を使ったため、多数決自体が壊れた位置で正しいサンプルが「ビット増加」に見えていた。7サンプル時点で期待値まで682だったのも偶然 |
| OLEDの表示更新が5Vレールを揺らしている | 読み出し中にOLEDへ一切触れなくても誤り率は変わらず。**否定** |
| バンク切替直後の電源整定不足 | OLED更新後に `delay(250)` を入れたら誤りが約6,500→19,000バイトに**悪化**。**否定** |

### 突破口

8KB刻みでゼロ率を出したのが決定打でした。

```
  窓        A15 A14 A13   bank0   bank1   bank2   bank3
  0x0000     0   0   0    100.0%  100.0%  100.0%  100.0%
  0x2000     0   0   1    100.0%  100.0%  100.0%  100.0%
  0x4000     0   1   0    100.0%  100.0%  100.0%  100.0%
  0x6000     0   1   1    100.0%  100.0%  100.0%  100.0%
  0x8000     1   0   0     16.1%   35.4%   73.9%    5.6%
  0xa000     1   0   1      9.0%   39.7%   31.2%    4.2%
  0xc000     1   1   0      4.6%   45.5%   10.8%    3.1%
  0xe000     1   1   1      0.7%   40.5%    3.2%    2.8%
```

**A15=0の領域が丸ごと死んでいる＝LoROM。** ヘッダの申告通りでした。

上位32KBを64バンク分集め直したところ、**一発で通りました**。統計的なマージも再試行も不要。

```
checksum = 0x4bca  計算値 = 0x4bca
CRC32    = 232bb5b8 → No-Intro "Super Mario Collection (Japan)" と完全一致
```

**教訓: ROMが自己申告しているものは、まず信じる。自分の推論より優先する。**

## 第8章 高速化 — 「1回おきの取りこぼし」

当初331µs/バイト（2MBで約12分）でした。内訳はほぼ全部が待ち時間で、
ROMの実力（アクセスタイム120〜200ns）から見て500倍以上過剰です。

### 一度目の挑戦と失敗

`digitalWrite`/`digitalRead`（1回約4µs）をポートレジスタ直叩きに置き換え、
ボーレートも1Mbpsへ。速度は12倍出ましたが、**データが壊れました**。

ここでまた誤診を重ねました。

| 仮説 | 実際 |
|---|---|
| ポート直叩きで同時スイッチングノイズが増えた | アドレスは毎回+1なので遷移するビットは平均2本程度。この説明は苦しい |
| 長時間の連続動作による電圧降下 | 外部電源でも変化なし |
| デカップリング不足 | 制作者から「既に最短距離で実装済み、33µF搭載済み、GNDも両方引いている」と回答。**打つ手は尽きていた** |

### 決定打

同じバンクを10回読み、**毎回きっかり30966バイトの相違**という結果が出ました。
ノイズなら数値がばらつくはずです。完全に決定的でした。

そこでアドレスの進み方を検算したところ:

```
そのまま      : 5.5%
2倍速         : 66.7%
半分(重複読み): 32768/32768 (100.0%)  ★
```

**`出力[i] == 正解[i÷2]` が100%一致。同じアドレスを2回ずつ読んでいました。**

Nano-1がストローブを**きっかり1回おきに取りこぼしていた**のです。
ポーリングには「ループを一周する間に来たパルスを取りこぼす」という原理的な穴があり、
Nano-1の処理時間がNano-2の1サイクルより長くなると**必ず半分落ちます**。

パルス幅を60µs、100µsと広げていたのは、この穴を塞がずに誤魔化していただけでした。
電源もデカップリングも無関係で、**純粋なソフトウェアの取りこぼし**でした。

### 解決 — ポーリングから割り込みへ

Nano-1/Nano-3を**ピン変化割り込み（PCINT）**に変更。
エッジをハードウェアがラッチするので、ISRが動く前にパルスが終わっていても取りこぼしません。
穴そのものが消えます。

その後、待ち時間を5段階で振り、**各条件で2回読んで両方とも正解と完全一致した場合のみ合格**
という基準で掃引しました（単発の一致を信じて痛い目を見た教訓の反映。実際PULSE=60は
単発では完全一致したのに、繰り返すと数千バイト化けた）。

```
RD=20 ADDR=20 PULSE= 5 -> 合格 (79us/byte)
RD=10 ADDR=10 PULSE= 3 -> 合格 (57us/byte)
RD= 5 ADDR= 5 PULSE= 3 -> 合格 (47us/byte)   ← 採用
RD= 3 ADDR= 3 PULSE= 2 -> 合格 (42us/byte)
RD= 2 ADDR= 2 PULSE= 2 -> 合格 (40us/byte)
```

最速値ではなく1段手前を採用したのは、カートの接触状態のばらつきに対する余裕のためです。

**331µs → 47µs/バイト（7倍）。2MBが約12分から約3分になりました。**

## まだ分かっていないこと

- **長時間の連続読み出しで壊れる**現象を、当初は電源の問題と考えていました。
  真因がNano-1の取りこぼしだったと判明した今、この現象も同じ原因だった可能性がありますが、
  **未検証**です。割り込み版で長時間の通しダンプを試せば白黒つきます
- Nano-2の制御ピンはまだ `digitalWrite` のままで、47µsのうち約34µsがそのオーバーヘッドです。
  ここをポート直叩きにすれば **15µs/バイト（2MBで約1分）** が見込めます

## 全体を通しての教訓

1. **ヘッダのチェックサム欄が通っても、ROMが正しいとは限らない。** 全バイト総和で検証する
2. **ROMの自己申告（map mode、サイズ）は自分の推論より信頼できる**
3. **単発の測定を信じない。** 2回一致してようやく候補、CRCが合ってようやく確定
4. **決定的か確率的かを見分ける。** 毎回同じ誤りならノイズではなく論理の誤り。
   これが最大の突破口になった
5. **数値の規則性を疑う。** `出力[i] == 正解[i÷2]` に気づけたのは、ずれ方を総当たりで
   検算したから。「壊れている」で止めずに「どう壊れているか」を測る
